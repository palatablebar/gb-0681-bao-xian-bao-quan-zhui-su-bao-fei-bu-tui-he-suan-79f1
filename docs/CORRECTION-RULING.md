# 隔离补正裁决：保留原证据，另立后继批次（append-only 修订链）

## 一、裁决

**补正不得覆盖原批次。** 原批次一经保存即为不可变审计证据；复核员的就地补正生成一个**后继批次（successor run）**，通过修订链（lineage）挂在原批次之后。工作台与结案下载在同一修订链上只呈现/导出**当前唯一有效（head）结论**，旧批次只读、可追、不可再发布或导出。

## 二、为什么不能覆盖原批次

| 约束 | 覆盖原批次 | 另立后继批次（采纳） |
|---|---|---|
| 审计要求原隔离值/原因/补正依据始终可追 | 原值被改写，证据链断裂，无法解释“从何改来” | 原批次原样冻结，后继批次携带 `before/after/basis` 修订台账，双向可追 |
| 保存失败恢复旧版本 | 覆盖写到一半失败即证据损坏 | 后继批次在独立事务中整体提交；失败回滚，原批次与 head 指针不变 |
| 同源重跑不新增修订/重复导出 | 幂等键被改写，难以区分重跑与修订 | 重跑命中既有 `run_id`（`INSERT OR IGNORE`）；补正由 lineage 登记，同一份补正重复提交返回同一后继批次 |
| 一份可发布结论 | 历史结论消失，看似只有一份但无法举证 | 链上唯一 head 才允许发布/导出，旧批次标记 `superseded`，结论唯一且历史完整 |
| 唯一去向 | 无法回答“原隔离记录去哪了” | 每条隔离记录在后继批次台账中有且仅有一条 disposition |

“就地补正”的操作体验保留（复核员在原批次工作台直接发起），落地方式是**派生后继批次**而非就地改写。

## 三、领域模型与状态机

### 3.1 批次状态（runs.lifecycle）

```
active（有效，链头，可复核/可发布/可导出）
   │  以本批次为 parent 成功补正
   └──> superseded（被取代，只读，不可复核/不可导出）
```

- 新批次保存即为 `active`。
- 后继批次与父批次状态切换在**同一事务**内完成；任何一步失败整体回滚，父批次仍为 active，旧版本自动保留。
- 已 `superseded` 的批次：复核返回 409，导出返回 409；GET 仍可读，保留全部原证据。
- 复核（通过/退回）仍走乐观锁版本号（TRAP-26 不变），且只允许在 active 批次上操作。

### 3.2 修订链 lineage

| 字段 | 含义 |
|---|---|
| `lineage_id` | 同一来源的所有批次共享的链 ID，首代为原批次 `run_id` |
| `parent_id` / `successor_id` | 父子指针，首代 `parent_id` 为空 |
| `correction_no` | 链内补正序号，首代为 0，逐次 +1 |
| `source_sha256` | 原始输入字节哈希，链内不变 |

### 3.3 补正台账 corrections（后继批次内，逐条不可变）

```json
{
  "line": 51,
  "id": "00901",
  "code": "MISSING",
  "before": {"annual_premium": "N/A"},
  "after": {"annual_premium": "3650.00"},
  "basis": "保全批单2026-09补件第3页",
  "operator": "reviewer-a",
  "created_at": "2026-11-19T…Z"
}
```

每条原隔离记录在台账中有**且仅有一条**去向：
- `CORRECTED`：用补正后取值重入管线；
- `REJECTED`：确认无效，维持隔离（仍须填写依据，记录留痕）。

后继批次完成条件：父批次 `quarantine` 中每一条（按来源行 `line` 定位，冲突为整组）都被恰好处置一次；重复或遗漏提交被拒绝（422）。

## 四、同一保单同时缺保费 + 冲突时两种做法的差异

以脏样例口径构造一张同时命中 MISSING 与 CONFLICT 的保单：

| 维度 | 覆盖原批次（否决） | 另立后继批次（采纳） |
|---|---|---|
| 当前结论数量 | 若就地改值后冲突行又被“最后覆盖”，结论数随改写手法漂移（冲突整组消失或只留 1 条），且无法复原当时取舍 | 确定性：冲突整组按一条 REJECTED/CORRECTED 组处置，缺值按一条处置，重算后该保单结论唯一，数量由台账决定并可复算 |
| 下载内容 | 只有改写后的单份 CSV，原值与原因丢失 | 只导出 head 的单份 CSV，但内含修订台账区块（原值、原因、依据、前后值），一份文件同时给出结论与证据 |
| 可解释性 | 复核无法回答“原值是什么、为什么改” | 正式结论经 `lineage + corrections` 追到修订前后的每个值 |

## 五、落地规则（与现有代码的契约）

1. **幂等**
   - 同源重跑：`identity(content, params, rule_version)` 不变 → 同 `run_id`，`INSERT OR IGNORE`，不新增批次、不重复导出（既有行为不变）。
   - 同一份补正（同 parent + 同台账内容哈希）重复提交：返回已存在的后继批次，不新建第二条修订。
2. **后继批次身份**：`successor_id = identity(parent_id + canonical(ledger) + rule_version)`，与原始输入身份区分；后继批次保存父来源字节哈希，链内可回溯到原始字节。
3. **重算**：后继批次由“原始字节 + 补正台账”确定性派生新 CSV（WIDTH 行替换整行；MISSING 替换字段；CONFLICT 整组替换为授权取值或整组拒收），再完整跑 M1–M7，不做局部打补丁，保证对账口径一致。
4. **对账加一栏修订平衡**：`父隔离数 = CORRECTED 数 + REJECTED 数`，不平衡不得置为 active/不可下载。
5. **工作台**：默认打开链 head；历史面板标注 `active/superseded` 与 `#补正序号`；提供“查看原批次证据”入口（只读）。隔离面板对 head 显示每条隔离的处置去向。
6. **结案下载**：仅 active 且对账平衡的 head 可导出；导出 CSV 在运行清单/对账/计算/隔离之外增加“修订台账”记录类型，checksum 覆盖全部区块（含台账），保证导出文件自证完整。
7. **失败恢复**：补正提交、head 指针切换、状态翻转共用一个 SQLite 事务（WAL），异常即回滚，旧版本继续可用。
8. **审计链完整性**：正式结论 → `lineage` → 父批次 → 原始 `source_b64` 与每条 `corrections.before/after/basis`，逐值可追。

## 六、验收不变量（对应 tests/）

1. 补正后父批次仍存在且 quarantine/raw 原样未改（证据冻结）。
2. 后继批次为链上唯一 active；父批次变 superseded；工作台列表与下载都只认 head。
3. 对 superseded 批次复核/导出均 409；GET 200 且证据可读。
4. 同一补正重复提交返回同一 successor_id，不新增修订；同源普通重跑不新增批次。
5. 台账处置数 = 父隔离数（冲突按组），缺漏/重复处置 422；无依据补正 422。
6. 模拟保存失败后父批次仍 active、可导出，旧版本完整。
7. 导出 CSV 含修订台账区块，checksum 随台账内容变化且稳定。
8. 缺保费 + 冲突并存保单：head 中该保单结论唯一、数量确定，原值与依据在台账可追。
